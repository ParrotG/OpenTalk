# 测试与验收规范

## 1. 使用方式

本文件集中维护验证工具、自动用例、集成场景、人工业务验收及运行准备。全部测试采用“模块 → 测试（工具／用例／场景）→ 预期”三列，编号用于需求和问题引用。

**（未完成）**表示缺少必要用例／实现或有效验收证据；保留模块、操作和预期，不省略要求。已有测试代码不等于目标环境已经通过，实际运行结果按文档与记录规范交接。单元／组件／集成按真实边界区分，不能把 offline 一律视为单元。

Python 测试在 tests/，浏览器测试在 frontend/tests/。Python命令默认从仓库根执行；pnpm命令从frontend执行。默认检查不调用付费服务，测试使用临时库。真实模型、录音和部署验收必须明确环境、费用与数据授权；不能写用户现有数据库获取测试通过。

## 8. 运行准备与命令

### 8.1 环境与隔离

后端Python 3.11／uv；前端Node.js 24／pnpm 10.13.1，分别锁定。干净专用环境可严格同步；已有用户环境使用保留额外包的方式：

```bash
uv sync --locked --python 3.11 --inexact
cd frontend
pnpm install --frozen-lockfile
cd ..
```

模型凭据在进程环境或根.env.local，已有环境优先，不打印秘密、不写NEXT_PUBLIC_*。DEEPSEEK_API_KEY对应当前LLM，SONIOX_API_KEY对应ASR/TTS。真实会话用专用sessions.toml改两个数据库路径，设置OPENTALK_SESSION_CONFIG供API／worker／CLI共享；录音及报告也用独立路径。New chat不清空数据库。

快速自动回归：

```bash
uv run --locked ruff check backend tests frontend/tests/fixtures
uv run --locked pytest -q
cd frontend
pnpm check
pnpm test
cd ..
```

默认pytest和浏览器套件不调用付费模型。UI测试自动启动3000，不复用已有实例；已有测试专用服务可设置OPENTALK_TEST_EXTERNAL_SERVER=1和OPENTALK_TEST_URL。Chromium首次安装用`pnpm exec playwright install chromium`，可能联网。RTC fixture需要livekit-server、锁定Python环境，18180–18183与18280–18283须空闲。

### 8.2 本地完整栈

四个终端分别执行，前三个从根运行；LIVEKIT_URL／LIVEKIT_PUBLIC_URL／key／secret与Server匹配，默认本机devkey／secret：

```bash
# Terminal 1: Media transport.
livekit-server --config config/livekit-local.yaml
# Terminal 2: Session control API.
PYTHONPATH=backend uv run --locked python -m opentalk.sessions.api
# Terminal 3: Agent worker.
PYTHONPATH=backend uv run --locked python -m opentalk.voice.worker dev --no-reload --log-level info
# Terminal 4: Browser frontend.
cd frontend
pnpm dev
```

打开http://localhost:3000。独立文字CLI为`PYTHONPATH=backend uv run --locked python -m opentalk.voice.text`，管理命令不调用模型，普通输入需要LLM。console需要PortAudio／本机设备及LiveKit凭据；网页／Docker不需要PortAudio。API8080／worker health8081；更换后端代码需重启，不是只刷新网页。

### 8.3 显式付费组件与浏览器

先准备录音、输出目录、隔离配置和有效凭据：

```bash
PYTHONPATH=backend uv run --locked python -m opentalk.llm.smoke
PYTHONPATH=backend uv run --locked python -m opentalk.asr.replay /tmp/opentalk-audio/input.wav --output /tmp/opentalk-audio/asr.json
PYTHONPATH=backend uv run --locked python -m opentalk.tts.smoke --text "你好，欢迎使用OpenTalk。How can I help you today?" --output /tmp/opentalk-audio/tts.wav --report /tmp/opentalk-audio/tts.json
```

ASR用PyAV解码、20ms实时分片、EOF追加3秒静音并有界等待，不等于收到finished回执。TTS增量提交后用句子缓冲，测试保存WAV、不实时播放，--cancel-after可取消。首结果耗时包含连接／回放或分句，不等于纯模型延迟。

真实浏览器录音目录包含input.wav、interrupt.wav、resume.wav，分别为记忆信息＋长答请求、打断＋短答请求、询问此前信息；从frontend执行：

```bash
OPENTALK_TEST_EXTERNAL_SERVER=1 OPENTALK_LIVE_AUDIO_DIR=/tmp/opentalk-browser-audio pnpm test
```

### 8.4 Docker隔离验证

常规本地运行用`docker compose up -d --build --wait`；健康不保证媒体或真实provider通过。离线容器测试不挂载用户数据：


### 8.5 环境限制

uv／Playwright缓存不可写时选可写路径并保持安装／运行一致。Node／pnpm混入Windows路径时核对实际可执行文件；端口、浏览器、文件权限或asyncio线程池停滞先在普通终端验证，不用应用特例绕过。API健康但无音频时查ICE、TCP7881／UDP7882和播放权限，同机LiveKit配置不能直接用于远程设备。

E-04／E-05 使用已人工检查的真实索引产物，先启动固定版本 Qdrant，再执行入库和底层查询：

```bash
docker compose --profile rag up -d --wait qdrant
INDEX_PATH=data/documents/<document-id>/parses/<parse-version>/indexing/hierarchical-v2
PYTHONPATH=backend uv run --locked --group rag \
  python -m opentalk.documents.index_vectors "$INDEX_PATH"
PYTHONPATH=backend uv run --locked --group rag \
  python -m opentalk.documents.search_vectors \
  "<evaluation-query>" \
  --document-id <document-id> \
  --parse-version <parse-version> \
  --index-profile hierarchical-v2 \
  --limit 10
```

若入库报告 token 超限，保留失败 manifest，并以新的 indexing profile 降低 chunk 上限后重做 2A；不能提高配置上限来绕过模型真实上限。E-05 的查询集和判断至少记录 query、预期相关节点／页面、实际 top-k、分数、漏召回和误召回。底层 dense 命令只验证 embedding 与数据库载荷，不验收 Hybrid、父块展开或 Agent 回答质量。

R-05 使用同时含 dense 与 lexical vector 的新 collection。旧 `opentalk_documents_multilingual_mpnet_v1` 不删除；按上面的 `index_vectors` 命令重跑每个需检索的索引目录，即会幂等写入配置中的 `opentalk_documents_multilingual_mpnet_hybrid_v1`。然后运行独立 Retrieval：

```bash
PYTHONPATH=backend uv run --locked python -m opentalk.documents.retrieve \
  "<standalone-query>" \
  --alternate-query "<optional-alternate-query>" \
  --document-id <document-id> \
  --parse-version <parse-version> \
  --index-profile hierarchical-v2 \
  --limit 6
```

检查 JSON 中的 `queries`、`result_count`，以及每条 evidence 的 `matched_text`、`context_text`、`expansion`、`page_numbers`、`section_path`、`provenance`、`asset_references` 和 `local_image_paths`。父块存在时 `expansion=parent`；只有层级缺失时才应为 `neighbors`。同一查询至少与 `search_vectors` 的 dense-only top-k 对照，记录 hybrid 新增的正确候选和新增误召回。

R-06 先保持 Qdrant 运行并完成新 collection 入库，再从仓库根执行用户验收入口：

```bash
PYTHONPATH=backend uv run --locked python -m opentalk.voice.text --agent conversation
```

依次输入一个文档内事实问题、同义追问、包含精确编号的问题、表格／公式问题、图片内容问题和一个明显不在文档中的问题。检查 session 诊断中的 `business_result` 含 `name=search_documents`；回答应说明相关页码并受返回证据约束。图片只有在工具以 `include_images=true` 调用且当前 LLM provider 支持图像输入时进入该轮临时多模态上下文；会话历史不应出现图片 base64。
