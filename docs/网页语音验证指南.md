# 网页语音验证指南（阶段 2、3）

## 范围与实现

`frontend/` 基于 LiveKit 官方 `agent-starter-react` 裁剪。采用简洁的聊天布局：底部文字输入／语音切换、Agent 音量波形、无标题与边框的 transcript，以及顶部可折叠的 Recent sessions / Services。跟随系统切换深浅色；用户消息使用有色气泡，助手文本不加框，两者不显示角色标签。没有预约面板、摄像头、屏幕共享、avatar、Cloud sandbox 或模型配置界面。预约仍可作为后端工具测试用例，业务服务不参与前端会话管理。

前端使用官方 `useSession`、`useAgent`、`useSessionMessages` 和音频播放组件；波形复用 Agents UI 的 WebGL 组件，根据音量和 Agent 状态变化，不是精确 PCM 测量仪。源码出处、固定提交和 MIT 许可见 [UPSTREAM.md](../frontend/UPSTREAM.md)。Python 依赖和 `uv.lock` 未调整；前端依赖使用 pnpm 独立锁定。

## 分段启动与测试

### A. 独立检查前端（无需模型调用）

Node.js 24、pnpm 10.13.1；在项目根目录执行：

```bash
cd frontend
pnpm install --frozen-lockfile
pnpm typecheck
pnpm build
pnpm exec playwright install chromium
pnpm test
```

默认 Playwright 用例自动启动端口 3000 的开发服务。测试历史渲染、用户发言片段合并、异常会话不可恢复、后台服务不可用、麦克风授权被拒绝、系统深浅色切换、移动折叠布局，以及同源代理；不调用付费模型。真实语音用例默认跳过。若已有前端服务，使用 `OPENTALK_TEST_EXTERNAL_SERVER=1 pnpm test`，不要再启动同端口服务。

只看页面：`pnpm dev`，访问 `http://localhost:3000`。未启动后台时 Services 显示不可用，Start voice 与文字输入不可用。

### B. 启动完整本地链路

根目录 `.env.local` 保留 Soniox / DeepSeek 凭据，并按本地开发服务器配置：

```dotenv
LIVEKIT_URL=ws://localhost:7880
LIVEKIT_PUBLIC_URL=ws://localhost:7880
LIVEKIT_API_KEY=devkey
LIVEKIT_API_SECRET=secret
```

四个终端分别运行；前三个从项目根目录启动：

```bash
# Terminal 1: LiveKit transport
livekit-server --config config/livekit-local.yaml

# Terminal 2: Independent SQLite session control service
PYTHONPATH=backend uv run --locked python -m opentalk.sessions.api

# Terminal 3: Real voice worker
PYTHONPATH=backend uv run --locked python -m opentalk.voice.worker dev --no-reload --log-level info

# Terminal 4: Browser frontend
cd frontend
pnpm dev
```

访问 `http://localhost:3000`，允许麦克风。无需 Python 本地音频设备、PortAudio 或 LiveKit Cloud。worker 首次处理房间需要初始化进程及 VAD，前端最长等待 45 秒；未成功连接会尝试结束已分配的 attempt，不将失败伪装为成功。

可以改为 `pnpm build` 后 `pnpm start`。`dev` 是当前锁定 Python SDK 的可用入口，SDK 会提示该命令已弃用；本阶段没有因此升级依赖。

API 默认 8080，worker 原生 HTTP 健康端口固定为 8081，前端 3000。`frontend/.env.local` 可设置仅服务器读取的 `OPENTALK_API_URL`，默认 `http://127.0.0.1:8080`；`OPENTALK_AGENT` 默认 `booking`，设为 `conversation` 时只运行通用 talkbot。恢复时代理读取已保存的 agent key，避免错误切换业务类型。

`config/livekit-local.yaml` 设置开发模式、info 日志、显式 `127.0.0.1` ICE 地址、回环候选和本机 UDP 绑定，继续使用 `devkey` / `secret`，不需要额外配置密钥。worker 同样使用 info 日志，减少默认 DEBUG 的传输细节。该配置用于浏览器与后端在同一台电脑上的测试，包括 Windows 浏览器访问 WSL 的 localhost；Docker 使用单独的媒体网络配置，启动与验证见 [Docker验证指南](Docker验证指南.md)；远程设备需另行配置可达媒体地址。

修改 worker 健康地址时，对 worker 设置 `OPENTALK_WORKER_HEALTH_HOST` / `OPENTALK_WORKER_HEALTH_PORT`，对 API 设置对应 `OPENTALK_WORKER_HEALTH_URL`。内部 `LIVEKIT_URL` 与浏览器 `LIVEKIT_PUBLIC_URL` 可以不同。远程浏览器需 HTTPS/WSS 与正确网络配置；浏览器的 localhost 指浏览器所在机器，不能指代远程后端。

### C. 人工验收

1. Services 的 Session API / LiveKit / Agent worker 为 `ok`，Model configuration 为 `configured`。
2. 点击底部右侧波形图标（Start voice），授权麦克风：输入框替换为波形和 Agent 状态，新会话出现欢迎语并播放音频。右侧 ×（Cancel voice）关闭麦克风、停止后端音频输出与正在运行的 TTS，切回文字输入，保留当前会话连接；原来的 LLM 回复继续流式输出文本，不重新执行工具。
3. 可直接输入文字并按 Enter 发送；Shift+Enter 换行。首次文字发送不申请麦克风权限，使用 LiveKit 原生 `lk.chat` 通道。文字模式不启动 TTS，文本直接流式输出，不随音频播放速度同步。输入中英混合语音时，字幕修订按照稳定的 `lk.segment_id` 覆盖同一消息；修订流的 stream ID 变化不会留下旧版本。助手尚未输出文本前连续的用户片段合为一个显示气泡，后端原始历史不合并。
4. 回复期间说话打断：音频停止，新的输入进入 transcript，后续回复对应新请求。可取消语音，再点击波形图标重新启用。
5. 不再显示 Resume session / End conversation 按钮。原生消息提交后自动保存 history / userdata；事件写入合并 50 ms，避免按 token 或字幕修订频繁写库，周期心跳仍作为兜底。点击 New chat 或选择其他历史，会内部关闭当前连接，等待后端完成保存，再切换。
6. 刷新或关闭后重新打开网页，自动展示上次选中的历史，不自动打开麦克风或调用模型；下一次发送文字或点击 Start voice 自动接续。也可从顶部 Recent sessions 选择 completed 历史后直接输入。session ID 不变，attempt ID 更新；询问上一轮提过的信息，模型应能接续。New chat 清空本地选择，新会话不继承旧上下文。本地存储仅保存 session / attempt ID 和关闭意图，不保存密钥、token 或聊天正文。
7. 强制断网或关闭进程：后端判定异常后显示 failed，允许看历史、不允许恢复。单纯关闭网页会通过 beacon 请求正常结束；后台给媒体断开留出 2 秒等待关闭请求，网页重开时仅重试本浏览器记录的同一 attempt 关闭意图，不结束其他连接的 attempt。beacon 不能保证送达，只有后端确实提交 completed 才允许接续。保存中的会话暂时只读并轮询结果。
8. 最近列表提供最新 20 个 session；回看展示最近最多 200 个原生历史项中的用户／助手文本，工具和系统内容保留在后端历史中。实时展示最多 200 条消息。完整历史可通过分页 API 或文本 `/session history` 检查。

预约测试只通过语音提出查询或编辑，不增加专门界面。修改预约会真实写入业务数据库；本轮自动语音验收使用通用 agent，没有执行预约写入。自然语言业务安全和非阻塞语言优化延续后续阶段。

修改后重启会话 API 和 worker（`--no-reload` 不会自动加载代码），再刷新页面。仅刷新前端而保持旧 worker，会缺少 `opentalk.set_voice_mode` RPC。此 RPC 仅允许当前 attempt 关联的用户调用，确认 RoomIO 和用户加入事件就绪后才应答；文字输入等待应答再发送，避免首条消息在初始化期间丢失。

## 服务可用性检查

前端每 10 秒调用同源 `/api/control/health/services`，服务器代理到后端 `/health/services`：

| 项目 | 检查内容 | 限制 |
| --- | --- | --- |
| Session API | SQLite 可访问 | 不代表所有磁盘写入都能成功 |
| LiveKit | 使用后端凭据调用 list_rooms | 不代表浏览器的媒体端口可达 |
| Agent worker | 原生 HTTP `/` 及 `/worker` 的 agent name | 不保证实时 dispatch 容量或下一次任务成功 |
| Model configuration | 读取 provider 配置，检查相应凭据存在 | 不检查账户余额、凭据有效性或服务商网络 |

检查有超时，不创建房间、不调用付费 provider、不向浏览器返回配置路径、内部异常或密钥。会话 API 连接失败时，Next.js 服务日志输出英语诊断，同类日志最多每 30 秒一条。普通 `/health` 继续保留原来的轻量 SQLite 检查。

## Windows / WSL localhost 媒体连接故障

如果服务全部显示 `ok` / `configured`，但报 `Connection failed: could not establish pc connection`，错误发生在 WebRTC PeerConnection / ICE 媒体连接阶段。麦克风许可、WebSocket 7880 和 API 检查通过，都不能保证 UDP 7882 / TCP 7881 的媒体候选可达。页面中的服务名称改为 LiveKit API，避免把 API 可用误认为音频已经连通。

当前机器采用 WSL mirrored 网络。默认 `livekit-server --dev` 自动选择局域网地址，Windows 浏览器通过 localhost 访问时，这个地址对应的媒体路径无法建立连接。修正必须同时指定回环 ICE 地址、开启回环候选与 UDP 绑定；只改 `LIVEKIT_PUBLIC_URL` 或只授权麦克风无法改变服务端发送的媒体候选。

停止旧的 LiveKit Server（第 1 个终端 Ctrl+C），从项目根目录改为：

```bash
livekit-server --config config/livekit-local.yaml
```

其余启动命令和 localhost URL 保持一致，等待 worker 重连后刷新页面并重新点击 Start voice。这不是修改全局防火墙、VPN 或 WSL 设置；配置只改变本机 LiveKit 的媒体监听与候选地址。

本轮实际对比（Windows Chrome 154、LiveKit Server 1.13.8、锁定的浏览器 SDK 2.22.2）：

| 浏览器位置 | 默认局域网 ICE 地址 | 本机回环配置 |
| --- | --- | --- |
| WSL/Linux 内 | 连接成功 | 连接成功 |
| Windows | 复现 `could not establish pc connection` | 连接成功，选中 UDP `127.0.0.1` |

测试在隔离端口运行，通过临时房间建立真实 WebRTC 连接和发布数据，不 dispatch Agent、不调用模型、不创建用户持久化 session；原有服务进程和会话记录保持不变。前一轮语音验证在 WSL 内浏览器运行，不能覆盖这条 Windows → WSL 媒体路径。

## 可重跑的真实浏览器测试

`frontend/tests/live.spec.ts` 是显式开启的真实集成用例。通过 Web Audio 将 WAV 输入送入浏览器麦克风轨道，其余链路使用实际 WebRTC、原生 worker、Soniox ASR/TTS、DeepSeek 和 SQLite。它会调用付费模型，并产生测试会话。

推荐复制 `config/sessions.toml` 到单独路径，将 session / telemetry 数据库指向 `/tmp` 的两个独立文件。API 与 worker 必须同时设置 `OPENTALK_SESSION_CONFIG=/absolute/path/to/test-sessions.toml`；文本入口也支持该覆盖。前端用 `OPENTALK_AGENT=conversation`，确保测试与预约业务数据无关。

准备同一目录下的三段单声道 WAV，例如：

```bash
mkdir -p /tmp/opentalk-browser-audio
PYTHONPATH=backend uv run --locked python -m opentalk.tts.smoke --text 'Please speak English. My name is Alice. Tell me a detailed story about a friendly robot exploring the ocean.' --language en --output /tmp/opentalk-browser-audio/input.wav --report /tmp/opentalk-browser-audio/input.json
PYTHONPATH=backend uv run --locked python -m opentalk.tts.smoke --text 'Stop the story. Just say ready.' --language en --output /tmp/opentalk-browser-audio/interrupt.wav --report /tmp/opentalk-browser-audio/interrupt.json
PYTHONPATH=backend uv run --locked python -m opentalk.tts.smoke --text 'What is my name? Reply in one short sentence.' --language en --output /tmp/opentalk-browser-audio/resume.wav --report /tmp/opentalk-browser-audio/resume.json
```

服务启动后，在 `frontend/`：

```bash
OPENTALK_TEST_EXTERNAL_SERVER=1 OPENTALK_LIVE_AUDIO_DIR=/tmp/opentalk-browser-audio pnpm test
```

测试验证浏览器音频元素处于播放状态、WebRTC 接收音频能量、真实字幕、麦克风切换、说话打断的原生 interrupted 标记、正常完成、同 ID 新 attempt 恢复、模型记忆、历史 ID 去重、新会话隔离以及异常断线禁止恢复。实时 provider 可能有延迟或转录差异，失败需结合保存历史与 worker 日志判断。

沙箱环境可将 `PLAYWRIGHT_BROWSERS_PATH=/tmp/opentalk-playwright` 同时用于安装与运行，将 `UV_CACHE_DIR=/tmp/opentalk-uv-cache` 用于 uv；这是当前环境的缓存路径选择，不是项目固定要求。
