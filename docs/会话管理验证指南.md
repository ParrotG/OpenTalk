# 会话管理与持久化验证

## 当前范围

本阶段实现独立 SQLite 会话服务、正常结束后的恢复、文本管理命令，以及供下一阶段网页使用的控制 API。没有开发网页或执行麦克风测试。没有新增或升级依赖：HTTP 使用锁文件中已有的 aiohttp，tracing 使用 LiveKit 已有的 OpenTelemetry SDK。

会话基础设施位于 `backend/opentalk/sessions/`。它不访问 BookingRepository、预约表或业务审计。`voice/factories.py` 是业务组合边界；当前可以选择 `booking` 或没有预约工具的 `conversation`。以后增加业务 Agent 只需增加对应 factory，不改会话存储。

## 官方接口与存储边界

- `session.history`：原生消息、工具调用和工具返回的来源。使用 `ChatContext.to_dict()` 序列化，保留原生 ID、时间和 interrupted 标记；排除音频、图片、metrics 和配置事件。
- `session.userdata`：使用显式 `SessionState` dataclass，保存 session ID、attempt ID 和 preferred_response_language。框架不自动将其持久化；应用负责序列化。
- 恢复：使用 `ChatContext.from_dict()`，通过 Agent 构造参数 `chat_ctx` 注入历史，重新应用当前系统规则。恢复已有工具返回只提供上下文，不执行工具，不恢复执行锁或旧轮次授权。
- 指标：使用模型插件的 `metrics_collected`、原生消息 `metrics` 和 `session.usage`。不订阅已弃用的 session 级 metrics_collected。
- Tracing：可选使用官方 `set_tracer_provider()` 接入 OpenTelemetry；默认关闭。开启后 native spans 保存到诊断数据库，过滤对话内容和工具参数，保留耗时、父子关联和 token 数量。
- 房间的 `JobContext.make_session_report()` 适合结束后导出报告；文本入口没有 JobContext，且本项目已经保存原生历史和指标，因此本阶段不重复保存完整报告。

恢复后 SDK 的新 session.history 记录当前 attempt 的新内容，Agent.chat_ctx 包含恢复的上下文。SQLite 按原生 ID 合并各 attempt，提供完整逻辑会话历史；不修改 SDK 的私有 history 属性。

独立配置在 `config/sessions.toml`：

| 数据 | 默认位置 | 保存方式 |
| --- | --- | --- |
| 会话索引、运行 attempts、userdata、原生历史 | data/sessions.sqlite3 | SQLite 事务与稳定 ID upsert |
| 指标、诊断事件、可选 trace spans | logs/telemetry.sqlite3 | 稳定事件 ID upsert、条数与时间保留限制 |
| 预约与业务审计 | config/backend.toml 指定的原业务数据库 | 保持原有业务模块 |

当前不再周期性重写 logs/voice 下的完整 JSON，不再复制预约审计、完整 generated_text、工具参数与工具返回到多份日志。原有 JSON 文件保留为历史产物，不自动导入。

临时 ASR 字幕用于实时展示，不逐次持久化。最终对话保存自原生历史。消息 metrics 与历史分开保存；相同 ID 的后续修订更新原记录。

## 生命周期与恢复

同一个 session_id 表示一段可继续的对话；每次启动或恢复产生新的 attempt_id。房间名包含两者，每次恢复使用新房间。状态为 pending、active、completed 或 failed。

只有 completed 可以恢复。completed 表示会话已关闭、最终历史和 userdata 在同一事务成功保存；模型和资源关闭失败也会将该 attempt 标为 failed。

- `/session end`、`/quit` 和正常 EOF：正常结束。
- Ctrl+C、异常退出、不可恢复的模型错误、持久化失败：failed，不允许恢复。
- 进程被强制终止：无法即时写最终状态；默认活动租约 60 秒后，在下一次查询、列表或启动操作中标为 failed。
- 没有连接的 room allocation：默认 900 秒后过期，时间与初始 token 有效期一致。
- 网页需要先调用 end API，等待 completed 后断开。未请求结束的参与者断连保守地视为 failed；短暂网络抖动与浏览器重连留待网页阶段验证。

正常结束后的恢复没有必须推迟的框架障碍，本阶段已实现。恢复不是恢复旧音频播放、未完成事务或运行中的生成任务。

历史归档保留全部实际对话，存储量随真实对话线性增长；不自动删除用户历史。每次恢复只读取最近 120 项上下文，清理截断处不完整的工具交换；每次 LLM 请求也限制上下文项数。历史浏览接口分页，不一次返回所有会话。

诊断待写队列默认最多 512 条，溢出计数写入 usage 记录；诊断数据库总量最多 10000 条、保留 7 天。队列、数据库条数和时间上限均可配置。当前运行最长 3600 秒，达到上限视为异常结束，限制 SDK 自身历史和事件在单次运行中的持续累积。保留上限包括 metrics 与可选 traces，不适用于用户对话归档。

## 文本验收

按原命令启动：

```bash
PYTHONPATH=backend uv run --locked python -m opentalk.voice.text
```

管理指令不进入模型上下文，也不调用付费 API。仅查询列表、历史和状态无需模型密钥。首次正常文本输入、`/session new` 或 `/session resume` 才初始化模型。

```text
/session help
/session
/session list
```

默认仍是 BookingAgent。要独立验证 talkbot 和会话服务，不加载任何预约数据：

```bash
PYTHONPATH=backend uv run --locked python -m opentalk.voice.text --agent conversation
```

恢复验收：

1. 输入“请用英语回复”，再告诉它一个容易核验的信息，例如“我的项目名是 OpenTalk”。
2. `/session` 获取 session_id，`/session history` 查看当前历史。
3. `/session end`，检查输出状态为 completed。
4. `/session resume <session_id>`，检查 session_id 相同、attempt_id 改变。
5. 问“我的项目叫什么？”，核对模型收到此前历史，回复偏好仍为英语。
6. `/session history` 检查没有重复历史；`/session end` 再结束。
7. 退出并重新运行程序，`/session list`、`/session show <session_id>` 后再次恢复，验证跨进程持久化。

异常验收：另建 session，输入一轮后 Ctrl+C；重新运行并尝试恢复该 ID，应返回 not_resumable。活动 session 和不同 Agent 类型也拒绝恢复。每轮保存及正常关闭保存都可重复执行，不追加重复消息或工具调用。

可用命令：

```text
/session
/session list [limit]
/session show ID
/session history [ID]
/session new
/session end
/session resume ID
/session help
/quit
```

`/session history` 展示最近 100 项并报告总数。`/session show` 包含运行 attempts。可以用 `--session-config` 指定单独配置和验收数据库，避免与日常会话混用。

## 网页控制 API

```bash
PYTHONPATH=backend uv run --locked python -m opentalk.sessions.api
```

默认仅监听 127.0.0.1:8080；下一阶段由 Next.js 同源转发。API 与 worker 使用同一个会话数据库和配置。API 不要求模型凭据，签发连接 token 需要 LiveKit 服务端凭据。

| 接口 | 语义 |
| --- | --- |
| GET /health | 检查服务与数据库 |
| POST /sessions | 幂等创建或恢复 session，返回连接详情和短期 token |
| GET /sessions?limit=20&offset=0 | 分页列表 |
| GET /sessions/{id} | 当前状态和 attempts |
| GET /sessions/{id}/history?limit=100&offset=0 | 分页原生历史 |
| POST /sessions/{id}/end | 请求对应 attempt 结束 |

创建请求：

```json
{"request_id":"demo-create-1","agent":"conversation"}
```

恢复请求使用新的 request_id，保留原 Agent 类型：

```json
{"request_id":"demo-resume-1","agent":"conversation","resume_session_id":"<session_id>"}
```

返回 serverUrl、roomName、participantName、participantToken 和 session。token 仅允许该房间连接与媒体／数据发布订阅，并包含具名 opentalk-booking dispatch 和 session/attempt metadata。这个 worker 名称当前可承载两种 Agent，实际类型由受管理的会话记录决定。

结束请求：

```json
{"attempt_id":"<current_attempt_id>"}
```

活动会话返回 202；worker 在心跳检查时收到结束请求，关闭原生会话、保存最终检查点，再清理房间。客户端轮询 GET /sessions/{id} 直到 completed 或 failed。pending 会话结束标为 failed/not_started。旧 attempt 的结束请求不会终止已经恢复的新运行。结束后的重复请求可以继续尝试房间清理。

`LIVEKIT_URL` 是 API／worker 连接服务的内部地址；`LIVEKIT_PUBLIC_URL` 覆盖浏览器地址，否则使用配置中的 public_livekit_url。房间 worker 仍通过以下命令启动：

```bash
PYTHONPATH=backend uv run --locked python -m opentalk.voice.worker dev
```

本阶段用签名 token 和模拟 LiveKit API 验证控制接口，尚未实际验证 Server dispatch 与浏览器连接；这部分属于下一阶段。

## 离线验证

```bash
uv run --locked pytest -q
uv run --locked pytest tests/test_session_store.py tests/test_session_resume.py tests/test_session_api.py -q
```

新增验证包括并发 claim、请求幂等、事务失败回滚、心跳过期、正常恢复、语言状态、工具返回不重放、异常／取消拒绝恢复、诊断队列与存储保留上限、trace 内容过滤、CLI 管理指令、签名 token 和 API 结束信号。测试使用临时数据库与模拟模型，不产生供应商费用。

2026-10-07 验证结果：全量离线 96 passed、4 skipped，包含本阶段新增 18 项测试。原生上下文恢复、工具不重放、持久化与 provider 关闭失败、API 结束信号均通过。原命令的 /session help、当前状态、列表和 /quit 也完成进程级冒烟；真实模型回答和浏览器／Server dispatch 未在本阶段执行。
