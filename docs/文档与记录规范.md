# 文档与工作记录规范

## 1. 单一来源与写法

需求回答“要什么”，设计回答“怎样实现及为何”，测试回答“怎样证明”，问题回答“差距在哪里”。不在每份文件重复完整配置、接口或同一套命令。

docs 以中文为主，代码标识与协议字段保留英文。文字面向未参与对话的人：写明确主体、触发条件、结果与边界，不写“本轮”“用户此前已确认”或依赖聊天上下文的省略。

主文档只保持当前有效内容；不追加历史版本、修改日志、测试次数演变或已废弃方案。重要选择保留当前理由和代价即可。历史 diff、讨论和详细运行产物交给 Git／PR／测试系统，不另建文档 changelog。

区分现状、规范和待实现。数字阈值注明来自配置还是需求；不能把 provider 参数、timeout 或 demo 的经验写成性能保证。

## 2. AI 完成一项工作后更新哪里

| 工作影响 | 应更新内容 |
| --- | --- |
| 用户行为、范围或质量目标 | 需求规格；同步关联验收用例 |
| 技术选型、分层、跨模块接口、错误码、schema／权限 | 系统设计；必要时调整需求与测试 |
| 任务拆分、依赖、阻断或完成条件 | PR／工单或交接中的当前状态，不维护额外计划文档 |
| 测试新增／分类、命令、门禁或人工场景 | 测试与验收，使用模块 → 测试（工具／用例／场景）→ 预期的统一格式；未完成显式标记 |
| 配置、运行、部署或排错方式 | 测试与验收中的运行准备／场景；架构影响同步系统设计 |
| 规则已明确或工具门禁已接入 | 根目录 AGENTS.MD 和实际工具配置；同步更新待改进问题 |
| 暂未处理的实际差距 | 待改进问题：定位、影响、建议、验证出口；相同问题更新同一 ID |
| 纯内部实现且行为／接口无变化 | 通常不改需求或设计；交接说明“无文档契约变化”即可 |

文档整理不自动授权修改 README／根目录 AGENTS.MD／工具配置。是否修改这些入口以具体任务范围为准，不因规范要求扩大工作范围。

## 3. 当前状态如何维护

同一任务、问题或需求更新原条目，不重复追加；ID 不重用。完成的任务可以从当前待办移除，历史由 Git 保存；未验收不得标为完成。未定义需求保留空白占位，不填未经认可的猜测。

任务状态统一使用：待确认、待实施、进行中、待验收、阻断、完成。阻断说明具体缺失条件；任务归属、当前下一步和已有证据足以接续即可，不要求每天写日报。

## 4. 最小交接与验证证据

每次交付在 PR／工单或最终汇报中提供以下字段；没有这些系统时使用一份临时交接文件，不向主文档追加运行日志。

```text
任务／需求 ID：
代码定位：commit ID；未提交则注明工作区改动范围
完成行为：
接口／数据影响：
验证：命令、环境、通过／失败／跳过／未执行及原因
证据位置：测试输出或受控产物路径
剩余问题／下一步：
人工验收：场景、期望、实际结果、验收人；未执行明确注明
```

验证产物可记录运行时间、模型／配置摘要和音频数据来源以便复现，这些是证据而非主文档历史版本。不得存秘密、完整环境或无需保留的个人数据；录音与对话需控制访问。记录人不能将自己未执行的检查写成通过。

## 5. 完成定义

适用需求与契约一致；必要的检查已执行且有证据；风险与未执行项明确；当前任务／问题同步更新；链接可用；主文档不含过期描述。需要人工验收的任务在签收前为待验收，不能靠 AI 口头总结替代。
