# 实时语音与 SQL/edit Agent 验证指南

## 1. 当前方案

本指南介绍原生语音与 query/edit 工具流程。资源、用户、容量和所有权规则已按新业务库更新，详细自然语言用例见 [Booking Service 测试用例](BookingService自然语言测试用例.md)。

原生 LiveKit AgentSession 编排流式 Soniox ASR、DeepSeek LLM、工具和 Soniox TTS。Soniox endpointing 判定轮次结束，Silero CPU VAD 触发打断。关闭预生成和误打断自动恢复。

通用 ConversationAgent 位于 backend/opentalk/agents/base.py，负责原生流式节点、轮次、语言偏好、工具执行生命周期、日志和 escalate_reasoning。BookingAgent 继承它，只增加 query、edit 两个业务工具。其他 Workspace/provider 解耦本轮未扩展。

系统提示要求使用适合朗读的自然口语和简短句子，不使用表格、emoji、Markdown、代码块或视觉列表；SQL 和结构化参数仅用于工具调用。运行时上下文提供业务时区和固定的当前用户 UID，避免误解日期与预约归属；存储时间为 UTC。高强度分析也使用同样的口语要求。

## 2. 准备与入口

```bash
uv sync --locked --python 3.11
PYTHONPATH=backend uv run --locked python -m opentalk admin init --start-date 2030-01-02 --days 7
PYTHONPATH=backend uv run --locked python -m opentalk.voice.text
```

日期应晚于实际测试日期。种子提供用户、资源、示例时段和部分占用；edit 可以预约未预设的时间区间。默认时区已改为 Asia/Singapore，存储仍为 UTC。无 offset 的 edit 时间按该本地时区解析。

DEEPSEEK_API_KEY 从环境变量或根 .env.local 读取，环境变量优先。文本入口使用同一个原生 AgentSession，支持 Linux/WSL 标准输入，/quit、EOF 或 Ctrl+C 退出。不启动 ASR/TTS 或音频设备。

麦克风入口仍可运行：

```bash
PYTHONPATH=backend uv run --locked python -m opentalk.voice.worker console --list-devices
PYTHONPATH=backend uv run --locked python -m opentalk.voice.worker console
```

另需 SONIOX_API_KEY、PortAudio 系统库和可访问的音频设备。用户暂搁置 PortAudio 验证，本轮未再次打开麦克风。锁定版本的 Python console 仍可用，SDK 将其标注为 deprecated；它不同于[浏览器 Agent Console](https://docs.livekit.io/testing/agent-console/)。

房间模式使用用户已安装的本地服务，不依赖 LiveKit Cloud：

```bash

# 配置与该服务对应的 LIVEKIT_API_KEY / LIVEKIT_API_SECRET 后启动 worker。
```

根目录 .env.local 中应保留已有模型密钥，并添加：

```dotenv

LIVEKIT_API_KEY=devkey

```

这是 livekit-server --dev 的开发凭据，参见[官方本地运行说明](https://docs.livekit.io/transport/self-hosting/local/)。本项目锁定 SDK 的 console 虽不连接真实房间，但设置 server URL 后会初始化 LiveKitAPI，所以也需要这对凭据。缺少它们会报 either token, or api_key and api_secret, must be set；这个报错不表示正在使用 Cloud。环境变量优先于 .env.local，已经导出的空值也会阻止 dotenv 补充，因此要修正或 unset 对应环境变量。修改后重新启动 Python worker。worker 名字为 opentalk-booking，客户端需要显式 dispatch。当前已有独立会话／token API，前端尚未实现；没有启动、重配或安装 Server。会话管理见 [会话管理验证指南](会话管理验证指南.md)。

## 3. query：开放只读 SQL

query 接受一条 SQL，可联表、聚合、CTE、范围和 schema 查询。例如：

```sql
SELECT name, type, location, capacity, metadata FROM resources ORDER BY name;
```

```sql
SELECT a.* FROM slot_availability a
WHERE julianday(a.starts_at) > julianday('now') AND a.remaining_capacity > 0
AND NOT EXISTS (
    SELECT 1 FROM reservations b
    WHERE b.uid='demo-user' AND b.status='active' AND b.rid=a.rid
    AND julianday(b.starts_at) < julianday(a.ends_at)
    AND julianday(b.ends_at) > julianday(a.starts_at)
)
ORDER BY a.starts_at, a.resource_name LIMIT 10;
```

SQLite 时间比较推荐 julianday，避免 ISO 文本格式和 offset 差异。联表字段重名时应使用别名，便于解析返回的行。

query 使用 mode=ro 连接、query_only 和 authorizer，只允许读取、SELECT、递归和允许的函数；拒绝写入、ATTACH、PRAGMA、事务控制与扩展加载。默认最多 200 行、100000 VM 步、2 秒，公开配置在 config/booking_agent.toml；结果包含 columns、rows、truncated 和 max_rows。

当前本地 demo 允许读取全部业务数据，包括他人的预约；写入仅限固定用户本人的预约，后端执行所有权和容量约束。没有登录流程或远程管理员角色。空查询结果不代表 fully booked；prompt 要求区分没有配置区间、已占用和没有匹配过滤条件。房间列表不要求日期；用户允许其他日期时可直接跨日期搜索，一轮可调用多次 query。

## 4. edit：房间与区间预约编辑

参数为 action、resource、starts_at、ends_at；resource 可为精确名称或 rid，update 另支持 new_resource、new_starts_at、new_ends_at，省略替换字段保留原值。可选 uid 必须等于当前固定用户，不能代他人预约。

| action | 行为 |
| --- | --- |
| add | 预约给定区间；没有对应 slot 时创建 |
| delete | 取消精确匹配资源与区间的本人活动预约；其他用户不变，保留 cancelled 历史 |
| update | 原子移动对应预约，保留 booking ID |

没有固定确认词，没有额外确认工具，没有旧提案版本授权；所有权由固定当前 UID 确定并由后端检查。prompt 要求 Agent 先说明具体变更并询问，等后续用户自然同意后再调用 edit；更改细节时重新询问。

该确认要求由语言模型执行，业务工具不提供独立确认拦截；因此测试中的遵守行为不能视为任意输入下的确定性保证。edit 执行有效时间区间、本人所有权、并发容量、本人重叠预约、事务和 operations 检查，不允许随意 SQL 写入。

用户轮次与原生 tool call 生成稳定 request key；重试返回原业务结果，不重复创建预约或 operation，同 key 更改参数会被拒绝。同一轮多项 edit 各有独立 key。已开始事务在语音取消后仍会完成并记录结果，过期调用在开始前拒绝。

业务库使用用户／资源模型。Agent 只暴露 query、edit 和通用 escalate_reasoning；管理员通过 admin init/inspect/query/check 管理数据库。

## 5. 自然语言手动场景

逐轮输入，等待回复再继续：

1. `Can you list all the rooms currently available?`
2. `Today or any other day with an available slot.`
3. `I'd like Room A on January 2, 2030, from 09:00 to 10:00. Ask me before editing.`
4. 回答确认问题：`Yes, that works. Go ahead.`
5. 请求改时间，等它说明变更后回答“可以，请修改”。
6. 请求取消，等询问后回答 `Please proceed with the cancellation.`

核对 Agent 实际查询的数据与操作日志。修改前的请求、问题和拒绝应不产生 edit。LLM 输出与工具选择存在随机性，不以固定措辞作为验收标准。

混合语言输入保留原文；单独输入“请用英语回复”/“请用中文回复”或对应英文命令会设置显式偏好，并更新后续 TTS 的主要语言。没有 detected_language 字段。

## 6. escalate_reasoning

默认 profile 继续禁用 thinking。config/llm.toml 的 reasoning profile 当前设置同一模型、thinking enabled、reasoning_effort=high、8192 token 和 60 秒超时；参数位于配置，不硬编码模型标识。

Agent 可调用 escalate_reasoning(task, message?)。工具先向用户输出简短提示，随后执行一次流式高强度分析，将结论返回给默认 Agent，后续查询或编辑仍使用默认模型。每轮最多升级一次。结束、失败或取消不会修改默认 provider。

升级请求不带工具，task 需自包含，提供相关事实和查询结果。它无法访问数据库或直接写入。只收集 answer content，推理 trace 不输出、播报或存入会话日志。

这样处理是因为 DeepSeek 思考模式带工具请求需要完整回传 reasoning_content；当前原生插件未提供该完整回传，隔离分析请求避免本轮扩展协议。参见[官方 thinking 文档](https://api-docs.deepseek.com/guides/thinking_mode/)。

可手动要求“先简短提示，再用 escalate_reasoning 比较这两个已知方案；不要预约”，然后继续一个简单查询，检查只有一次 reasoning_started，并在 reasoning_finished 中恢复 default。供应商返回 usage 时记录 reasoning_usage。

## 7. 日志与验证结果

最新会话历史与 userdata 保存在独立 data/sessions.sqlite3；metrics、诊断和可选 traces 保存在 logs/telemetry.sqlite3。worker/console 定期保存，文本每轮保存，两者退出时保存。原生历史按 ID upsert，工具调用和返回只保存一次，不记录精确 spoken_text。旧 logs/voice JSON 属于历史产物；恢复规则与文本管理指令见 [会话管理验证指南](会话管理验证指南.md)。

业务库只保留 operations 保存幂等请求、成功结果和失败原因，kind 区分 add/delete/update；events 表和 operations.session_id 已移除。失败编辑回滚业务变更并保留 failed operation；Agent 诊断继续写入独立 telemetry，不与业务表混存。
